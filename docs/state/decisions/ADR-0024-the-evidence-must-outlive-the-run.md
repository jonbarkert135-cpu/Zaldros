# ADR-0024 — Доказательства обязаны переживать прогон

Дата: 2026-08-28. Статус: принято.

## Задача

Три места, где наш собственный канал доказательств терял данные или врал о них. Все три найдены
на живых прогонах `iso`, а не в рассуждениях.

1. **Красный прогон при полностью зелёной системе.** Прогон 33161289986: все три сборки и восемь
   из девяти загрузок прошли, а `boot (services, mid)` упал на шаге публикации:
   `! [remote rejected] ci-logs-boot-services-mid (cannot lock ref …: is at 413fab5 but expected
   4ffae63)`. Два перекрывающихся прогона force-push'ат одну ветку — проигравший получает отказ.
   Это гонка за ссылку, а не дефект Zaldros, но она красит прогон и обесценивает красный цвет.
2. **Диагностика, которой нет ровно тогда, когда она нужна.** `build-iso.sh` снимал свой EXIT-трап
   **перед** `mksquashfs` и `grub-mkrescue` — то есть вся вторая половина сборки (3 ГиБ дерева,
   сборка ISO) не оставляла ни одного диагностического файла, ни при успехе, ни при падении. Как
   следствие, `environment.txt` отсутствовал и после **успешной** сборки, шаг
   «Diagnostics summary» умирал под `bash -e` с кодом 1, это скрывал `continue-on-error`, и из
   summary вместе с ним пропадали **последние 200 строк лога сборки** — первое, что читают, когда
   сборка ломается.
3. **Проверка UEFI, которая спрашивала не то.** Каждая успешная сборка заканчивалась в логе
   строками `xorriso : FAILURE : Cannot find path '/EFI' in loaded ISO image` /
   `xorriso : aborting`. Ложная тревога: `grub-mkrescue` не создаёт каталог `/EFI`, он вкладывает
   FAT-образ `/efi.img` вторым образом в каталог El Torito. Настоящий факт («UEFI-образ есть»)
   лежал тремя строками выше и не проверялся никогда.

## Решение

**1. Публикация доказательств — отдельный скрипт с повторами.** `build/iso/publish-evidence.sh`
конвертирует PPM-кадры в PNG, коммитит каталог в ветку `ci-logs-*` и пушит с повторами
(`EVIDENCE_ATTEMPTS`, по умолчанию 5). Гонка за ссылку переживается; если не удалось после
последней попытки — шаг падает громко, потому что «зелёный шаг, ничего не опубликовавший» — это
та же ложь. URL с токеном никогда не попадает в лог: пуш идёт в именованный remote, а вывод
прогоняется через фильтр `https://…@` → `https://`. Задание, ничего не собравшее, всё равно
публикует ветку с `NOTE.txt` и меткой — читателю нужен ответ, а не пустое место.

**2. Трап не снимается до конца скрипта.** `collect_debug` теперь охватывает squashfs и сборку ISO,
и внутри функции стоит `set +e`: под `set -e` первый упавший зонд обрывал всю группу и оставлял
`environment.txt` дописанным до середины — обрезанная диагностика хуже отсутствующей, потому что
выглядит целой. Шаги summary в `docs/ci/iso.yml` больше не могут оборваться на отсутствующем
файле: каждый зонд заканчивается `|| echo "[почему файла нет]"`.

**3. UEFI доказывается каталогом El Torito.** `build/iso/verify-iso.py` разбирает вывод
`xorriso -report_el_torito plain`, и его код возврата — контракт для `build-iso.sh`:
`0` — UEFI-образ есть (в отчёт печатается его путь), `1` — каталог прочитан и UEFI-образа нет
(такой ISO не грузится на UEFI-прошивке, сборка падает), `3` — отчёт получить не удалось:
**UNVERIFIED**, что не «прошло» и не «упало». Зонд `-find /EFI` удалён вместе со своим ложным
FAILURE.

## Последствия

- Гейты: shell 465 passed + 2 skipped, tools 44.
- Новые тесты бьют по фактам, а не по хосту: публикация проверяется на настоящем локальном bare-репо
  и на заглушке `git`, которая проигрывает гонку дважды, затем пропускает пуш; отсутствие утечки
  токена — отдельным тестом; диагностика — реальным запуском `build-iso.sh` без root (тест
  пропускается, если запущен под root, иначе он начал бы настоящую сборку); вердикт UEFI — на
  дословном отчёте xorriso из прогона 33161289986.
- **Владельцу:** живой `.github/workflows/iso.yml` правит только он (GitHub App Виктора не может
  пушить workflow-файлы). Перенести из `docs/ci/iso.yml` три места: два шага публикации (теперь
  вызывают `publish-evidence.sh`) и «Diagnostics summary» с `|| echo`-зондами. Пока это не сделано,
  гонка за ссылку продолжит красить прогоны, а последние 200 строк лога сборки не будут доходить
  до summary.
- Не проверено: сам ISO по-прежнему не собран и не загружен на живом железе; `verify-iso.py`
  проверен на записанном отчёте, а не на свежесобранном образе — это подтвердит первый прогон `iso`
  после этого коммита.
