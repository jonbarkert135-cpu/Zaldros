# ADR-0021 — Зелёный гейт обязан что-то значить

Дата: 2026-08-28. Статус: принято.

## Задача

Первый настоящий прогон сборки показал две противоположные лжи в наших гейтах.

1. **CI был красным шесть коммитов подряд** (с `5f44ab9`, прогон 33124081665) из-за теста
   `test_the_shell_survives_a_machine_with_no_services_at_all`: `AssertionError: network`. Код при
   этом верен — падал сам тест.
2. **CI был зелёным там, где отчёт упал.** Прогон `iso` 33157358995 собрал все три ISO и загрузил
   девять образов, а матрица результатов в summary оказалась пустой:
   `build/iso/report.py` умер с `AttributeError: 'dict' object has no attribute 'splitlines'`,
   и шаг всё равно отчитался успехом.

## Решение

**1. Тест «машины без служб» должен быть машиной без служб.** Фасеты `network`, `bluetooth` и
`power` при отсутствии D-Bus честно откатываются в sysfs — значит, обрезав шины, тест продолжал
читать /sys той машины, на которой запущен. У раннера GitHub кабель поднят, и `network`
возвращал `available=True, value=None`: это ровно тот контракт, который записан рядом
(`_sysfs_status`: у Ethernet нет уровня сигнала, и придуманные «100 %» были бы ложью). Тест теперь
подменяет `sysfs_root` на пустой каталог и требует, чтобы **всё** было недоступно и объяснено.

**2. Контракт `Reading` записан тестом, а не только комментарием.** `available` значит «факт
настоящий», а не «есть число». Новый тест
`test_a_reading_may_be_available_without_a_number_and_the_seam_allows_it` закрепляет это на
проводном подключении без NetworkManager, чтобы инвариант «доступно ⇒ есть число» больше никто
не восстановил.

**3. `boot_time` — это словарь, и колонка это знает.** Гость измеряет время загрузки двумя
способами (`uptime` на момент self-test, плюс kernel/userspace, когда `systemd-analyze` отвечает);
колонка ждала текст `systemd-analyze`. Теперь принимаются обе формы, а «не измерено» печатается
прочерком, а не догадкой.

**4. `set -o pipefail` в шаге «Result matrix».** `python3 report.py | tee -a $GITHUB_STEP_SUMMARY`
возвращает код `tee`, поэтому падение отчёта было невидимым — и, что хуже, `report.py` возвращает
1 на любом непрошедшем бут-тесте, и этот код тоже терялся. Две строки добавлены в
`docs/ci/iso.yml` — рецензируемую копию, которую проверяет тест. **Живой
`.github/workflows/iso.yml` должен применить владелец:** GitHub App Виктора не имеет права
пушить файлы в `.github/workflows/` (`refusing to allow a GitHub App to … without workflows
permission`). Пока это не сделано, шаг «Result matrix» остаётся зелёным при упавшем отчёте —
записано в `TODO.md`, а не спрятано.

**5. `BUILD.md` больше не отрицает существование сборки.** Там был текст «the build has never been
executed»; заменён на то, что есть в логах: прогон 33157358995 на `b85017e`, три ISO,
`iso-full` 3 038 491 745 Б, девять загрузок из девяти, `KVM available` на раннере — и явный абзац
о том, что живого железа по-прежнему не было.

## Правило, которое из этого следует

Гейт формулирует утверждение о машине, а не о самом себе. Если тест может пройти или упасть
из-за хоста, на котором он идёт, он не гейт, а измерение хоста; если шаг может быть зелёным при
упавшем скрипте, он не гейт, а украшение.

## Чего нет

* Локальная сборка ISO в песочнице так и невозможна: в user namespace замаплен один uid, поэтому
  configure-фаза dpkg падает на `chown` (`dpkg-statoverride: … Invalid argument`), а `/dev/kvm`
  отсутствует. Реальный гейт — GitHub Actions или машина владельца; это записано в `BUILD.md`.
* Матрица из `report.py` проверена на подставленных JSON-файлах формы, которую пишет
  `selftest.boot_seconds()`; настоящий вывод после исправления увидим в следующем прогоне `iso`.
* На живом железе не проверено ничего.
