# План: от прототипа к проверяемой Linux-системе

## Цель первой версии

Предлагаемый рубеж — **developer alpha**, а не обещание эквивалентности Windows:
загрузка x86_64 VM в Wayland-сессию; работа с настоящими окнами; запуск и поиск
приложений; сеть, звук, файлы, уведомления, питание и настройки через Linux-службы;
понятные отказы и восстановление. Затем — установка на виртуальный диск,
обновления и recovery. Office и Wine идут отдельными расширениями после основы.

Ubuntu 26.04 и KWin/Qt сохраняются как текущая рабочая гипотеза ADR. Выбор
full/services/legacy остаётся открытым до сравнительного прогона актуального SHA.
Для первого воспроизводимого прогона использовать full как контрольный кандидат,
а не считать его автоматически победителем или запускать plasmashell в обход архитектуры.

## Приоритет и зависимости

Выполнять по номеру, сохраняя небольшие reviewable изменения. P01–P04 дают общую
основу; P05–P16 доводят пользовательские сценарии; P17 проверяет их вместе;
P18–P20 расширяют продукт. Если этап требует VM/оборудование, заверши независимую
часть и зафиксируй BLOCKED, но не перескакивай через обязательный gate молча.
Документы не заменяют разработку: каждый этап должен закончиться работающим
изменением, meaningful тестом либо конкретным воспроизведённым внешним блокером.

## Что означает «работает»

У каждого сценария пять независимых уровней доказательства:

1. UNIT — преобразование/валидация на фикстурах.
2. BUS — настоящий транспорт с тестовой службой.
3. SYSTEM — реальная Linux-служба в VM/целевой сессии.
4. E2E — действие пользователя → UI → backend → служба → независимый readback.
5. HARDWARE — сценарий на указанном устройстве/драйвере.

PASS на одном уровне не поднимает остальные. Статусы: PASS / FAIL / BLOCKED /
SKIPPED / UNRUN; реализовано и проверено — разные поля. Журнал хранит SHA, команду,
версии, среду, exit code, counts/skips и пути к артефактам. Нет процента готовности,
вычисленного по числу тестов или страниц настроек.

Обязательный результат изменения состояния: requested → authorizing/running →
succeeded/failed/cancelled/timed_out, плюс независимая проверка конечного состояния.
Accepted request или созданный PID — ещё не succeeded. Для операций без безопасной
отмены явно описать границу отмены и завершать последующее наблюдение.

## Контрольный сценарий alpha

Cold boot → вход обычным пользователем → Start → поиск и запуск двух внешних
приложений → taskbar/Alt+Tab/snap → сеть → звук/микрофон → создать/переименовать/
переместить/удалить/восстановить файл → уведомление → настройки экрана с rollback →
lock/unlock → suspend/resume → проверка обновлений → logout/relogin.
Ни один необходимый шаг не должен требовать терминала; диагностический доступ остаётся.
Перезагрузка службы посреди операции должна дать понятную ошибку и восстановление,
а не вечный spinner или зависание shell.

## Контроль объёма и решений

Не писать собственные ядро, пакетный менеджер, криптографию или офисный engine.
Сначала зрелые лицензируемые Linux-компоненты, собственный код только для пробелов UX.
Собственный D-Bus transport не менять по вкусу: P04 сравнивает maintenance/correctness,
поддержку FD/async/reconnect с библиотекой и оформляет ADR на измеренном прототипе.
Не уменьшать безопасность и не убирать функциональность ради RAM или визуального паритета.

Сроки намеренно не выдуманы: после P04 и P17 переоценить объём по фактическим дефектам.
Требуется внешний ресурс: Linux VM host с root/full namespace, диском, QEMU и желательно KVM;
для Wi-Fi/BT/suspend/GPU — выбранное реальное железо. Не выдавать его отсутствие за дефект кода.
Не запускать удалённый CI, публикацию, запись дисков или push без соответствующей авторизации.
