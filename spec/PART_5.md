# RAVEN OS (→ Bedrock Linux) — MASTER SPECIFICATION — PART 5/5 — QA, PERFORMANCE, AUTONOMOUS DEVELOPMENT & FINAL ACCEPTANCE
Received 2026-08-23 (Slack DM). Final part. Combine PARTS 1–5. Naming: see docs/NAMING.md.
"After receiving this part, begin by reviewing the complete specification and identifying conflicts, missing requirements, technical risks and architectural contradictions. Do not blindly implement the specification if research demonstrates a superior approach."

1. PERFORMANCE BENCHMARKING — automate: boot time, login time, idle RAM, idle CPU, GPU idle, background process count, service count, disk usage, application startup, UI latency, compositor performance, frame consistency, suspend/resume, battery. Baseline first. BASELINE → CHANGE → BENCHMARK → COMPARE → ACCEPT/REVERT.
2. PERFORMANCE TARGET — maximum practical performance without sacrificing stability, hardware compatibility, security or functionality. Never disable essential services just to lower a RAM number.
3. MEMORY OPTIMIZATION — investigate unnecessary daemons, background services, startup apps, indexing, caches, duplicated services, desktop effects, memory leaks, inefficient applications. Every optimization must be measured.
4. BOOT OPTIMIZATION — measure firmware→bootloader, bootloader→kernel, kernel init, userspace init, display manager, desktop startup, first usable interaction. Optimize measured bottlenecks.
5. APPLICATION STARTUP — measure Explorer, Settings, Notepad, Terminal, browser, Software Center, Task Manager. Optimize cold and warm start separately.
6. UI PERFORMANCE — test scrolling, window movement, resizing, animations, Start opening, Search opening, Explorer navigation, Settings navigation, multi-monitor. Hardware acceleration where appropriate; avoid animation-heavy UI that harms low-end hardware.
7. AUTOMATED TESTING — unit, integration, UI, regression, performance, security and boot tests.
8. VISUAL REGRESSION — screenshots of desktop, Start, taskbar, Search, Explorer, Settings, notifications, quick settings, dialogs, system utilities; objective comparison; track similarity over time.
9. REFERENCE TESTING — WINDOWS REFERENCE → BEDROCK IMPLEMENTATION → SCREENSHOT/RECORDING → COMPARE → IDENTIFY DEVIATIONS → FIX → RETEST. Compare appearance *and* behaviour: a visually similar component that behaves incorrectly is NOT complete.
10. HARDWARE TEST MATRIX — Intel, AMD, NVIDIA, Intel GPU, AMD GPU, Wi-Fi, Bluetooth, laptop, desktop, external displays, touchpad, audio, USB — each SUPPORTED / TESTED / PARTIALLY TESTED / KNOWN ISSUE.
11. BUILD PIPELINE — SOURCE → BUILD → PACKAGES → ROOT FILESYSTEM → BOOTABLE IMAGE → VM TEST → INSTALLER → PHYSICAL HARDWARE TEST. Every build carries version, Git commit, build metadata, test results.
12. ISO / IMAGE — bootable image supporting UEFI, a secure-boot strategy if implemented, live environment where practical, graphical installer, recovery, hardware detection.
13. GIT WORKFLOW — commit meaningful changes with description, recorded tests and relevant benchmarks. Never silently overwrite known-good code.
14. DOCUMENTATION — README, ARCHITECTURE.md, BUILD.md, INSTALL.md, RECOVERY.md, SECURITY.md, PERFORMANCE.md, COMPATIBILITY.md, CONTRIBUTING.md, THIRD_PARTY_LICENSES.md, CHANGELOG.md.
15. DEVELOPMENT PHASES — 0 Research & architecture · 1 Minimal bootable Linux base · 2 Graphics + compositor + basic desktop · 3 Bedrock Shell · 4 Taskbar + Start + Search · 5 Explorer · 6 Settings · 7 System utilities · 8 Application management · 9 Windows compatibility · 10 Installer + recovery · 11 Performance optimization · 12 Hardware compatibility · 13 Security audit · 14 Release candidate.
16. DEVELOPMENT PRIORITY — 1 correctness, 2 stability, 3 security, 4 hardware compatibility, 5 usability, 6 performance, 7 visual similarity, 8 advanced features. Never sacrifice stability merely for visual similarity.
17. DEFINITION OF DONE — system boots; installer works; desktop, taskbar, Start, Search, Explorer, Settings work; networking, audio, Bluetooth, GPU acceleration, multi-monitor, file associations work; terminal works; PowerShell integration tested if included; Task Manager and system management tools work; software installation, updates and recovery work; security baseline verified; regression tests pass.
18. WINDOWS → BEDROCK FEATURE MATRIX — per Windows capability: implementation, status, test, notes. Statuses: IMPLEMENTED / PARTIALLY IMPLEMENTED / ALTERNATIVE IMPLEMENTATION / NOT IMPLEMENTED / NOT APPLICABLE. Never hide limitations.
19. FINAL AUDIT — architecture, performance, security, hardware, UX, visual and reliability audits before release.
20. AUTONOMOUS AGENT RULE — investigate, research, plan, implement, build, test, inspect logs, debug, benchmark, optimize, document, repeat — without being told each step. But request confirmation before destructive operations: formatting disks, deleting partitions, modifying the host OS, destructive hardware operations, irreversible data deletion.
21. SAFE DEVELOPMENT — never assume the development machine is expendable. VM → snapshot → test → revert. On physical hardware: recovery media, backups, documented changes, no destructive operations without confirmation.
22. FAILURE HANDLING — do not hide failures, do not claim success, do not silently remove failing functionality. Reproduce → collect logs → root cause → hypothesis → test hypothesis → fix → rerun tests → regression test.
23. SELF-CRITIQUE — after every major phase: what is weak, unnecessarily complex, resource-hungry, safely removable, simplifiable, fragile, under-tested, missing, or likely to break on different hardware? Then improve it.
24. FINAL GOAL — familiar Windows 11-style desktop; complete everyday OS; genuine Linux architecture; minimal background overhead; strong hardware support; practical Windows app/game compatibility; strong transparent security defaults; usable without learning Linux first.
25. FINAL INSTRUCTION — combine PARTS 1–5; summarize requirements; identify contradictions; identify missing pieces; research current technologies; compare architecture options; select the optimal Linux base; justify every major decision; produce the complete architecture; create the roadmap; begin with PHASE 0. Research first. Measure. Build. Test. Compare. Optimize. Repeat. "The objective is not to create a Linux distribution with a Windows theme" but the best possible Windows-like Linux desktop operating system.
